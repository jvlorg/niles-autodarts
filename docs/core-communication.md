# Add-on ↔ Niles core communication inventory

Scope: checked-in add-on sources and pinned WIT contract. Niles household room/satellite authority and speech execution remain core-owned. The repository-pinned contract describes this component’s integration surface; it does not establish compatibility with an installed Niles version.

## Event ingress and session lifecycle

The component’s HTTP timer polls status and baseline information; it is separate from the host-managed WebSocket event ingress. The component opens the optional connection when announcements are enabled, routes bounded text frames through `AnnouncementSession::ingest_json`, invalidates on malformed/non-text input and resets on connection lifecycle changes. Stale callbacks are ignored. The core session parses and invalidates automatically on parse failure; callers must not silently drop malformed input. Settings changes and reconnects require a new clean baseline. A nonempty initial snapshot suppresses the entire existing collection and later appends; only a clean empty/count-zero state restores eligibility. HTTP snapshots may initialize/reset baseline but cannot be promoted to real-time append events. See [`component/src/lib.rs`](../component/src/lib.rs) and synthetic lifecycle cases in [`component/src/tests.rs`](../component/src/tests.rs).

## Speech and audience boundary

The component opens the pinned room-bound speech stream when its separate setting is enabled. `SpeechDelivery` submits announcement text and polls asynchronous outcomes; component shutdown closes owned WebSocket and speech handles. The session-facing `AnnouncementDelivery` trait still supports recording and explicit unavailable adapters for core-level use. The host/core must resolve and authorize household identities and own speech execution, delivery/error policy and actual output. Configured audience values do not prove that the host resolved them, and the checked-in room-bound speech path does not establish arbitrary multi-room or selected-satellite routing. No notification substitution, private API, sidecar or direct satellite writes are proposed.

## Candidate total and order policy

The local contract is per-dart announcements as the API reports them in Each dart → Total mode, and no dart announcements in TotalOnly. The first `motion_state.isTakeoutPartial == true` or `isTakeoutFull == true` completes an eligible cached local collection once; later markers are suppressed. This local detection total is not a game-authoritative score or game-turn judgment. If throws shrink/clear first, retain a bounded last validated pre-removal snapshot; shrink by itself never announces, but a later explicit marker can complete that snapshot. TotalOnly clear-before-marker also preserves the eligible cached collection and remains silent until the explicit marker. If evidence suggests correction, is invalid/out-of-order or otherwise ambiguous, suppress. After removal/clear, require a clean empty count-zero baseline before another collection. Source events provide no reliable timestamps, so no timestamp semantics are inferred. These are add-on policy rules, not proven universal Board Manager semantics or live compatibility.

Target lists are sorted and deduplicated. Delivery attempt keys include connection epoch and collection serial and are recorded before calling the adapter, preventing an uncertain failure from being retried as definitely unheard. Disabled intent, mode/audience change and reconnect reset the reducer and require a new clean empty baseline. Synthetic recording-adapter proof is add-on policy only, not proof of installed transport, household resolution or audible speech.
