# Niles Autodarts — canonical plan

## Goal status

The local candidate implements bounded Board Manager JSON ingress, strict dart parsing, clean-baseline gating, one/two/three-dart local collection policy, explicit takeout handling, and exactly-once total selection. A third validated dart arms one logical one-second deadline; explicit takeout may complete the same round earlier. Deadline expiry is supplied by the component and never uses a clock in core.

The component uses `/api/events` for scoring ingress and an optional room-bound Niles speech stream. Speech intents are admitted into a bounded FIFO with one host request in flight. The next intent waits for the exact correlated terminal host outcome, including failure, cancellation, replacement, rate limiting, and no-satellite outcomes. Pending and polling errors retain the in-flight request. Stop, disablement, reconfiguration, reconnect, parse errors, overflow, and observed stopped input invalidate stale generations; ordinary takeout and round clear do not.
Detection control is asynchronous and generation-scoped. A successful `/api/start` or `/api/stop` response is acknowledgement only; response timeout is dispatch-uncertain, not provider rejection. The component returns `Ok(())` for acknowledged or uncertain monitoring, keeps the last validated `on` observation unchanged, and reports `Starting`, `running`, rejection, readback unavailability, and monitoring expiry separately. Only validated, connected/non-disconnected, non-`Starting` observations confirm a requested state. Contradictory `Starting/running:true` and disconnected samples cannot invent a stopped or running value. Each accelerated callback performs at most one bounded state read; a monotonic 30-second deadline starts before dispatch and is checked before and after readback, independently of timer delivery or registration. Duplicate commands do not extend it. After expiry, only a new definitive observation can release the unresolved-operation latch.
The supplied historical receive-only observation reported `Starting/running:false` at `2026-10-24T14:06:14.079583Z` and `Started/running:true` at `2026-10-24T14:06:29.655414Z` (15.575831 seconds). The new startup fixture and component tests use that interval as labelled synthetic timing; the reduced JSON capture does not contain those timestamps. The later Niles/provider HTTP 429 `token_quota_exceeded` remains a separate speech/provider failure and is not addressed by detection control.

Current observation shortcuts expire after the configured ordinary polling interval and are invalidated by unavailable readback or connection lifecycle changes. Valid current WebSocket state envelopes can confirm progress; malformed or oversized envelopes cannot update detection state before full ingress validation. Operation identity and elapsed time appear in diagnostics. Suppression is in-memory only: component stop/restart or reconfiguration resets it, and no exactly-once remote execution across those boundaries is claimed.

The component now reports `command_connection` as an unknown command outcome rather than rejection: the pinned host exposes the same connection error when sending fails before dispatch and when an incomplete response follows a request that may have executed. It still returns the host's generic error result, so a user may receive an error/apology even if a later observation shows the board running. Complete HTTP non-2xx responses remain genuine rejection; timeout and oversized-response cases remain uncertainty. The add-on does not parse human error text, invent dispatch evidence, or retry blindly.

**Separate host-contract follow-up:** A6 remains unsupported by the pinned Niles 0.5.0 contract. The host must expose dispatch-phase evidence before the add-on can classify unreachable and post-dispatch incomplete responses differently. This is a concrete core decision, not an add-on implementation claim or a reason to modify Niles in this revision.

This is a local implementation candidate. The add-on requirements covered by this revision are synthetic component behavior and compiled loopback host proof; installed-host compatibility, general live Board Manager event ordering, audible delivery, household routing, and selected-satellite behavior remain deferred. The compiled proof requires the pinned host and free loopback port 3180. Local sums are detection-derived values, not X01 authority.

## V1 — local Board Manager score announcements and detection control

V1 uses only the configured local Board Manager. No cloud account, match feed, X01 authority, game selection, match outcome, bust, checkout, or special/game speech is claimed. Detection on/off is distinct from physical power, reset, and game creation.

The parser accepts bounded `{type,data}` envelopes, at most three darts, strict integer counts, valid segment ranges, and bull values. Multiplier zero is accepted only for the evidenced canonical outside miss shape: `number` 1 through 20, `bed` exactly `Outside`, `name` exactly `M<number>`, and multiplier `0`; it occupies a detected dart slot and scores zero. Ordinary nonzero scoring inputs do not require name or bed fields. Malformed or contradictory miss fields are rejected. Omitted `throws` is canonical only for `numThrows == 0`.

The reducer requires a clean empty baseline and accepts one append at a time. `Starting` is not a running baseline even if it reports `running:true`; disconnected or stopped input invalidates eligibility. Each dart mode emits each accepted score, including detected zeroes; Total only emits the completed total. A third validated append arms one deadline token once. Explicit motion (`isTakeoutPartial` or `isTakeoutFull`), exact state events (`Takeout started` / `Takeout finished`), and exact `status: Takeout in progress` are boundary evidence after full snapshot validation; third-dart `status: Takeout` alone is not. Takeout and matching deadline expiry share one exactly-once completion transition. A clear-bearing finish completes the cached candidate and preserves its empty baseline. One or two detected darts complete only on explicit takeout. Zero detected darts stay silent; a detected all-zero collection may announce total zero.

Clear or shrink alone never announces. A clear-before-marker sequence retains its eligible collection. Corrections, count jumps, malformed input, stopped input, reconnect, disablement, and settings changes invalidate eligibility and require a new baseline. A completed total retains immutable round content while later rounds enter the FIFO.

Removal episode latching is separate from deadline completion. Redundant state/motion takeout flags cannot complete a later round until explicit neutral motion rearms the episode. Queue overflow and either one-shot registration failure discard stale work and require a new baseline. Ingress validation and observed HTTP stop/disconnect run before FIFO draining, including accelerated detection readback during a pending start; acknowledged stop commands cancel stale work even if the independent state reread is still pending. This cancellation does not assert that detection has physically stopped. Timer generation identity survives component stop/restart.

`AnnouncementSession` owns validated settings, parsing, reducer state, deadline tokens, and JSON ingress. `pending_total_deadline()` exposes the logical token. `on_total_deadline()` is a no-op for stale, cancelled, completed, invalidated, or reset tokens. Request keys include connection epoch and collection serial; every delivery attempt is recorded before the injectable boundary. Adapter `Ok(())` means adapter acceptance only, never host submission, playback, or audibility.

Household membership, room audience resolution, speech authority, arbitration, synthesis, and final transport remain in Niles. V2 TV scoreboard and V3 game selection remain out of scope.

## Evidence and proof boundaries

The supplied installed alpha.2 observation is historical user evidence for revision `82a30c4155e6ba20806a00734042a1f4ea49c1a7`: audible hit and takeout-total behavior were observed, and captured outside misses exposed the narrow grammar above. That evidence does not make this candidate installed, released, generally compatible, routed, or audibly verified.

`board-manager-jvl14-three-round-reduced-capture.json` is the supplied deterministic 40-envelope reduced receive-only capture, preserved with its original ordered fields and omissions. The fixture is parsed and compared against an independent supplied-payload oracle before replay. The exact capture carries the three rounds `[60,20,7]`, `[40,20,0]`, and `[12,18,0]` through settings, JSON ingress, reducer policy, and recording delivery. `board-manager-jvl14-synthetic-scenarios.json` remains separate and covers partial rounds, deadline-first ordering, takeout-first ordering, and detected-zero behavior. Both modes produce totals 87, 60, and 30; Each dart → Total additionally preserves the nine detected dart values. The exact reduced capture is not live-provider timing evidence.

The exact-capture equality regression compares the complete parsed ordered JSON value, including the first `Starting` event's `running:false`, every envelope, field, and omission. The unchanged JVL-13 capture remains replayed; neutral motion and deadline/takeout schedules are added only to separately identified synthetic scenarios.
